# Golden cases

One case is one folder. The harness in `../harness.ts` discovers every folder here that has
a `case.json` and `../cases.test.ts` runs all of them, so adding a case is adding a
directory — no test file to edit.

```text
<case-name>/
  case.json           description, the profile, the seed
  situation.json      a literal Situation (schemaVersion 3)
  forced.json         optional; dice pinned by roll id (ADR-0011)
  expected.json       HAND-DERIVED from the SRD; a partial Outcome
  README.md           optional; how the expected outcome was derived
  trace.snap.txt      generated; the full trace as JSON
  narrative.snap.txt  generated; the trace as prose (NFR-7)
```

`case.json`'s `profile` is either a list of pack directories relative to the case folder, base
first (ADR-0018), or the slug of a profile `content/profiles.yaml` declares.

## A case rendered from a template

A case may carry `template.json` instead of `situation.json`, which is what makes NFR-4's
"a golden test for every template × profile" affordable — twelve cases are twelve four-line
files plus the outcome each one is actually about:

```text
<case-name>/
  case.json           "profile": "srd-5.2.1"   <- a slug, not directories
  template.json       { "template": "melee-attack", "params": {} }
  forced.json
  expected.json       HAND-DERIVED, exactly as above
  situation.json      GENERATED by the harness from the two above
```

The slug is named once, because it picks the fixture variant the template renders against as
well as the packs the run resolves (ADR-0026); saying it twice would let the two disagree. The
harness writes the rendered `situation.json` back out so the case stays replayable from the
command line, but it is a snapshot of an input — `template.json` is the source, and editing
the situation by hand achieves nothing.

**`expected.json` is written by hand and the two `.snap` files are not.** That asymmetry is
the whole design (NFR-4). `expected.json` is a claim about what the rules say, derived from
the SRD sections the pack's rules cite and checked with `toMatchObject`, so it must never be
regenerated from what the engine printed — if it disagrees with the engine, one of them is
wrong and that is the finding. The snapshots are a record of a *format*, which ADR-0010 and
ADR-0014 explicitly leave unstable apart from `seq` ordering and the event kinds; they are
expected to churn, are refreshed with `pnpm test -u`, and are reviewed as a diff.

They are asserted by separate `it`s for the same reason, so a trace-format change fails the
trace assertion alone and leaves the outcome, identity and determinism assertions green.

Any case can be replayed from the command line — same packs, same seed, same dice:

```sh
pnpm engine run \
  --packs packages/engine/test/golden/packs/srd-5.2.1-min \
  --situation packages/engine/test/golden/cases/<case-name>/situation.json \
  --seed golden \
  --forced packages/engine/test/golden/cases/<case-name>/forced.json \
  --narrative
```

A template case is replayed the same way, pointing `--packs` at the profile's pack directories
and `--situation` at the generated snapshot:

```sh
pnpm engine run \
  --packs content/dnd5e-srd-5.2.1 \
  --situation packages/engine/test/golden/cases/buffed-round-srd-5.2.1/situation.snap.txt \
  --seed golden \
  --forced packages/engine/test/golden/cases/buffed-round-srd-5.2.1/forced.json \
  --narrative
```
